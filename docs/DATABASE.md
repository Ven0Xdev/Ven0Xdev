# Database Design — Nexora AI Financial Intelligence Platform

| Field | Value |
|---|---|
| Version | 1.0 |
| Engine | PostgreSQL 16 + TimescaleDB (SQLite fallback for dev/CI only) |
| Migrations | Alembic (`backend/alembic/`), baseline `6bbad53f77a7` |
| Companion docs | `SYSTEM-ARCHITECTURE.md` §5 (why this engine) · `PRD.md` §10 |

Engine selection rationale lives in SYSTEM-ARCHITECTURE.md §5.1 (Postgres+Timescale vs. ClickHouse/Influx/Mongo). Summary: the prediction→outcome truth loop is relational and transactional — its integrity *is* the product — and Timescale gives the one genuinely high-volume time series (OHLCV) partitioning and compression inside the same database.

Deliberate design notes visible in the diagram:

- **`ticker_symbol` strings, not FKs, on predictions/news/trades/watchlist.** The universe registry (`tickers`) is a *cache of provider metadata*, refreshable and even rebuildable; predictions are *permanent evidence*. Chaining permanent rows to a mutable registry row via FK would make registry maintenance (symbol changes, provider swaps) a referential-integrity minefield. Symbols are the stable business key in this domain; the registry is looked up by symbol when needed.
- **`predictions ||--o| outcomes` is one-to-at-most-one, DB-enforced** via UNIQUE on `outcomes.prediction_id` — the evaluator's exactly-once contract survives even a buggy or concurrent evaluator.

## 2. Table-by-Table Specification

Types shown as PostgreSQL; SQLite fallback maps automatically. All autoincrement PKs are `INTEGER GENERATED BY DEFAULT AS IDENTITY` semantics via SQLAlchemy.

### 2.1 `tickers` — universe registry

**Why it exists:** local registry of the scannable universe with slow-moving metadata (tier, float, shares). A cache, not a source of truth — rebuildable from providers.

| Column | Type | Null | Default | Notes |
|---|---|---|---|---|
| id | int | PK | autoinc | |
| symbol | varchar(16) | no | | **UNIQUE**, indexed — business key |
| company_name | varchar(255) | no | | |
| tier | varchar(32) | no | 'Pink' | QX/QB/Pink/PinkLimited/Expert |
| exchange | varchar(32) | no | 'OTC' | |
| sector / industry | varchar(64/128) | yes | | |
| float_shares / shares_outstanding / market_cap | float | yes | | provider-supplied; EDGAR overrides at read time |
| is_active | bool | no | true | delisting soft-flag |
| reverse_split_count_3y | int | no | 0 | populated by EDGAR phase 2 |
| created_at | timestamp | no | now | |

Indexes: `UNIQUE(symbol)`.

### 2.2 `ohlcv_bars` — price time series (TimescaleDB hypertable)

**Why it exists:** locally persisted bars for symbols we track long-term — powering outcome evaluation and backtests without re-pulling vendors, and the only table with genuine millions-of-rows growth.

| Column | Type | Null | Notes |
|---|---|---|---|
| ticker_id | int → tickers.id | no | **PK part** |
| ts | timestamp | no | **PK part**, hypertable partition column |
| timeframe | varchar(8) | no | **PK part**; '1d'/'1h'/'5m'/'1m' |
| open/high/low/close | float | no | |
| volume | float | no | |
| bid / ask | float | yes | NULL when vendor supplies no depth (honesty rule P2) |

**Natural composite PK, no surrogate id** — the canonical Timescale layout (partition column must be in every unique constraint), and the earlier surrogate-id composite-PK design broke autoincrement (see §5, lesson L1). Index: `ix_ohlcv_ticker_ts (ticker_id, ts)` for range scans. Hypertable conversion is idempotent at startup and a no-op on SQLite.

### 2.3 `predictions` — immutable AI snapshots (the evidence log)

**Why it exists:** the platform's accountability record. Every scan cycle writes what the AI claimed; nothing ever updates it (append-only, arch D9).

| Column | Type | Null | Notes |
|---|---|---|---|
| id | int | PK | autoinc |
| ticker_symbol | varchar(16) | no | indexed |
| model_version_id | int → model_versions.id | yes | traceability (FR-506) |
| created_at | timestamp | no | indexed |
| current_price | float | no | CHECK > 0 |
| liquidity_score…confidence_score (8 cols) | float | no | CHECK [0,100] on overall/confidence/manipulation |
| prob_up_5 / _10 / _20 | float | no | **CHECK [0,1] each** |
| prob_downside_before_upside | float | no | CHECK [0,1] |
| entry_zone_low/high, ideal_entry_price, stop_loss, take_profit_1/2/3 | float | no | **CHECK strict ordering** stop < entry < tp1 < tp2 < tp3 |
| max_allocation_pct, risk_reward | float | no | |
| holding_period_days | int | no | CHECK > 0 |
| explanation | text | no | |
| horizon_probabilities / feature_snapshot / shap_top_factors | jsonb | no | `{}` default |

**Why CHECK constraints here and almost nowhere else:** this table feeds calibration — the product's honesty metric. A bug emitting probability 1.7 must fail at INSERT, not silently poison the truth loop. JSON columns hold display-shaped payloads (per-horizon matrix, SHAP factors) that are never filtered on — jsonb keeps them queryable later without schema churn.

Indexes: `ix_predictions_ticker_created (ticker_symbol, created_at)` — the history endpoint's exact access path; single-column `ticker_symbol` and `created_at` (evaluator's global chronological walk).

### 2.4 `outcomes` — realized grades

**Why it exists:** the other half of the truth loop; what actually happened after each prediction.

| Column | Type | Null | Notes |
|---|---|---|---|
| id | int | PK | |
| prediction_id | int → predictions.id | no | **UNIQUE** — exactly-once grading, DB-enforced |
| evaluated_at | timestamp | no | now |
| horizon_days | int | no | CHECK > 0; copied from prediction (evaluation basis is frozen even if policy changes) |
| realized_return_pct | float | no | close-to-close at horizon |
| hit_take_profit_1/2/3 | bool | no | barrier-touch semantics |
| hit_stop_loss | bool | no | same-bar tie → stop (P5) |
| max_drawdown_pct | float | no | **CHECK ≤ 0** |
| notes | text | yes | |

### 2.5 `model_versions` — model registry

**Why it exists:** every probability must be attributable to the exact artifact that produced it; retraining without provenance would make calibration history meaningless.

Columns: id PK · name · version · model_type (lightgbm/xgboost/catboost/ensemble/anomaly/forecast) · trained_at · artifact_path · training_metrics jsonb · hyperparameters jsonb · is_active bool.

### 2.6 `edgar_company_facts` — ingested SEC facts

**Why it exists:** architecture D7 — the request path never calls sec.gov; scheduled ingestion lands here and fundamentals read locally. One row per ticker (UPSERT semantics), not history — EDGAR itself is the history archive; we store the current derived answer plus enough to audit it (latest + year-ago share counts).

Columns: id PK · ticker_symbol UNIQUE · cik ('' = confirmed not-SEC-registered, itself a signal and a re-query suppressor) · shares_outstanding_latest / _year_ago · dilution_12m_pct (NULL = unknown, never fake-zero) · last_filing_date · last_periodic_form · filing_delinquent (nullable tri-state) · fetched_at (24h TTL gate).

### 2.7 `news_items`

**Why it exists:** persisted news flow for catalyst decay windows and (Phase 4) training the promotion classifier on labeled history. Columns: id PK · ticker_symbol · published_at · source · headline(512) · url · sentiment [-1,1] · is_press_release · is_promotional. Index: `ix_news_ticker_published (ticker_symbol, published_at)`.

### 2.8 `trades`

**Why it exists:** live/paper execution log, deliberately separate from backtest trades (simulated and real fills must never mingle in one table — queries "how did we actually do" cannot risk contamination). Columns: id PK · ticker_symbol · side buy/sell · quantity · price · executed_at · prediction_id (soft link) · status. Index: `ix_trades_ticker_executed`.

### 2.9 `backtest_results` / `backtest_trades`

**Why they exist:** named, reproducible experiment records — a backtest without its exact `strategy_config` JSON is an anecdote. Results hold the metric set (Sharpe, Sortino, max DD, profit factor, expectancy, win rate, avg hold, total return, num_trades) + date range; trades hold per-fill detail with exit_reason. FK `backtest_trades.result_id` indexed, cascade delete (children meaningless without the run).

### 2.10 `chat_sessions` / `chat_messages`

**Why they exist:** FR-803 — assistant memory that survives restarts and is auditable (what did the assistant actually tell users?). Sessions: session_key UNIQUE + ticker context. Messages: role CHECK-able ('user'/'assistant'), content, created_at; index `ix_chat_messages_session_created (session_id, created_at)` — the exact history-fetch path.

### 2.11 `watchlist_items` / `portfolio_positions`

**Why they exist:** user state. Watchlist: ticker UNIQUE (idempotent add), note. Positions: ticker, quantity, avg_entry_price, opened_at, status open/closed — closed rows are *retained*, not deleted (audit trail). Both gain a `user_id` FK in the FR-1100 migration (single-tenant today).

## 3. Index Strategy Summary

Every index exists for a named query; no speculative indexes.

| Index | Serves |
|---|---|
| `predictions(ticker_symbol, created_at)` | per-ticker history, newest-first |
| `predictions(created_at)` | evaluator's chronological scan; retention jobs |
| `outcomes(prediction_id) UNIQUE` | integrity + O(1) join to prediction |
| `ohlcv_bars(ticker_id, ts)` | bar range scans (evaluator, backtests) |
| `news_items(ticker_symbol, published_at)` | latest-news-per-ticker |
| `chat_messages(session_id, created_at)` | session history |
| `backtest_trades(result_id)` | run detail expansion |
| `trades(ticker_symbol, executed_at)` | per-ticker execution history |
| `edgar_company_facts(ticker_symbol) UNIQUE` | overlay lookup per analysis |
| `tickers(symbol) UNIQUE`, `chat_sessions(session_key) UNIQUE`, `watchlist_items(ticker_symbol) UNIQUE` | business-key lookups + idempotency |

## 4. Millions-of-Records Plan

Volume model at target scale (2,000 tickers):

| Table | Driver | Volume | Strategy |
|---|---|---|---|
| `ohlcv_bars` | 2,000 × 252 trading days | ~500k rows/yr daily; ~200M/yr if 1-minute bars ever land | Hypertable now; at intraday: `add_compression_policy` (compress chunks >7 days, ~90% reduction), continuous aggregates for daily rollups, `add_retention_policy` on raw minutes (18mo) |
| `predictions` | cadence × universe | 15-min cadence × 2,000 = **70M/yr — unacceptable**; policy change *before* scale: full snapshot hourly + write-on-change between (≥10-point score delta or new flag) → ~17M/yr | Yearly **declarative partitions** on `created_at` when >10M rows (PK becomes `(id, created_at)` — planned migration, documented so the composite-PK/autoincrement trap is handled deliberately this time via explicit sequence); BRIN index on `created_at` replaces B-tree at that scale (append-only = perfectly correlated, ~1000× smaller) |
| `outcomes` | ≤1 per prediction | bounded by predictions | partitions follow predictions |
| `news_items` | ~20/ticker/day cap | ~14M/yr worst case | 18-month retention prune (PRD); same partition playbook if exceeded |
| `chat_messages` | user-driven | linear in users | fine to 100M+; per-user pruning policy in FR-1100 |
| everything else | slow-moving | thousands | no action ever needed |

General disciplines: append-only tables never UPDATE (HOT-bloat-free, vacuum-friendly); JSON payloads are jsonb but never row-filtered (no GIN indexes needed); all timestamps UTC; `EXPLAIN ANALYZE` snapshots for the four hot queries land in CI at Phase 5.

## 5. Migrations

**Tooling:** Alembic, `backend/alembic/`. `env.py` pulls the URL from app settings (environment-driven, same DB the app would use) and `Base.metadata` from the models package — autogenerate always sees the full schema. `render_as_batch` enabled on SQLite so ALTERs work in dev.

**Migration log:**

| Revision | Purpose |
|---|---|
| `6bbad53f77a7` baseline | Full current schema: 14 tables, all constraints (CHECKs, UNIQUEs), all indexes above |

**Planned migrations (in order):**

1. `users` + `user_id` FKs on watchlist/portfolio/chat_sessions (FR-1100) — additive, backfill single-tenant rows to a seed user.
2. `predictions` snapshot-policy columns (`snapshot_kind` enum full/delta) preceding cadence change.
3. Partitioning migration for `predictions`/`outcomes` (>10M rows): new partitioned tables, dual-write window, backfill, swap — documented runbook required before execution.
4. Timescale compression + retention policies for `ohlcv_bars` (arrives with intraday data).

**Operational rules:**

- Runtime `create_all` remains only as the SQLite/dev bootstrap; Postgres environments run `alembic upgrade head` in the deploy pipeline **before** new code serves traffic (CI gate: autogenerate against head must produce an empty diff — models and migrations may never drift).
- Migrations are forward-only in production; down-revisions exist for development.
- Destructive migrations (drops, type narrowing) require a two-release deprecation window.

**Lessons encoded (from real defects in this repo):**

- **L1:** composite `(id, timestamp)` PKs silently break autoincrement → business tables keep single-column PKs; hypertables use natural keys with no surrogate (§2.2, §2.3).
- **L2:** DB-level CHECKs on the truth loop caught nothing yet — but the sub-penny rounding hazard they exposed in `_trade_levels` (stop == entry after 4dp rounding) was found *because* the constraint was written. Constraints are executable documentation.
